# Production test-account HTTP acceptance — pending execution

Companion to the [review-only rollout procedure](production-test-account-rollout.md). All cases below are **NOT RUN**. They become runnable only after release, account initialization and explicit HTTP-test authorization. This document contains no executable credential file or actual live finding.

## Private client and evidence rules

The future reviewed verifier reads passwords from the approved private file and keeps a separate cookie jar per identity in memory or a protected 0600 file. It must validate HTTPS certificates, enforce the exact approved origin, refuse redirects carrying secrets or cookies to a different origin, never disable TLS verification, and discard response bodies not needed for an assertion. Require release/fixture IDs to match the approval before any credential request.

No curl command containing passwords, shell substitutions that print them, request tracing, body logging, cookie/header dumps, HAR export, session recording, screenshots of URLs/credentials, raw database results or serialized exceptions. Check existing proxy/app/APM logging privately before sending secrets; if request bodies, Cookie/Set-Cookie headers, password-reset tokens or credentials are logged, stop for a reviewed remediation. Do not discover logging behavior using real credentials. Evidence records only case ID, identity alias, expected/actual HTTP status, safe assertion outcomes, release/operation reference and timestamp. Cookie values and password/token hashes are never evidence.

The browser API defaults to `/api`, forwarding API controller paths without that prefix. Confirm the deployed same-origin routing first; do not guess a new endpoint or send passwords to a different server. In the steps below, `O` is the independently verified `truevoice-testing` UUID, and `X` is a second **approved synthetic** organization UUID with no test-user memberships. No guessed live customer UUIDs or non-test content is used. If `X` does not exist, arrange its separately approved audited fixture creation; never borrow another customer's tenant for an isolation test.

## Common cases — repeat independently for every inventory identity

1. Empty private cookie jar. `GET https://voice.truevinecloud.online/api/auth/terms`: expect 200 and the configured current terms contract. Obtain a server-issued `tv_csrf` cookie through the deployed application flow; if it is unavailable, stop rather than bypass CSRF. Keep the body/cookie private.
2. `POST /api/auth/sign-in` with `{email, password}` read in memory from the private config, appropriate JSON content type, exact origin, `tv_csrf` cookie and matching `x-truevine-csrf`: first use **one** deliberately incorrect private candidate, expect 401/invalid-credentials contract and no session. Never probe `admin@truevoice.com`, repeat guesses or trigger lockout. Respect both identity/IP budgets; on 429 wait the configured interval and record the throttle. Do not disable limits or fabricate IPs.
3. Using fresh valid CSRF state, repeat with the configured correct password: expect 200 and `{ok:true}`. Check that `tv_session` is Secure, HttpOnly, SameSite=Lax, Path=/, is not in the body, and the CSRF cookie remains readable/Secure. The jar is a credential, never console output.
4. `GET /api/me`: expect 200, exact identity and role. Organization users have the expected sole test membership and no platform role; platform users have the exact platform role and no tenant membership. A wrong/missing role fails even if sign-in succeeded. Never use nonexistent `/auth/me` or `/auth/csrf` as substitutes.
5. The named custodian reviews/accepts current terms through the real `/accept-terms` flow when required (`POST /api/auth/terms/accept`, valid session/CSRF, expected 204). No provisioning-created acceptance or automatic legal consent. A terms-related denial is not an RBAC test result.
6. Execute the row below with valid session, terms and CSRF where required. For denials assert the actual permission/membership denial contract, not merely any 403; a CSRF, lockout, rate-limit or terms failure is inconclusive.
7. Every organization user: `GET /api/organizations/X` and `/api/organizations/X/campaigns` must reject access (current guard contract 403) without content. Every platform-only identity: customer `GET /api/organizations/O` must reject access without tenant membership. Do not treat platform rights as organization membership.
8. `POST /api/auth/sign-out` with session/CSRF: expect 204. A protected request with the captured old jar must return 401. Retire jars securely. After approved disable, repeat correct-password sign-in and stale-session checks for exactly the retired accounts; both must refuse.

## Mutation and remaining-permission coverage

For OWNER, ADMIN and CAMPAIGN_MANAGER, an additionally approved `POST /api/organizations/O/campaigns` with `{name: <unique synthetic fixture label>}` should return 201 and DRAFT; verify that exact tenant, creator and audit. A draft creation is the current implemented service behavior, but recheck the release for newly added dispatch hooks before authorizing it. Do not activate campaigns, enqueue paid operations, call a real number, collect money, add contacts, or send emails. Record created IDs for approved cleanup. A denied VIEWER/BILLING creation must leave no row or job.

Use the complete [registry matrix](../qa-role-permission-matrix.md) to enumerate other endpoint permission consumers for the exact release. Every planned mutating permission needs separately approved synthetic payloads, expected business preconditions, expected side effects and cleanup evidence; do not call membership invitations successfully when no email delivery is authorized. Ownership transfer, operational emergency stop, support-session/diagnostic access, billing updates and contact imports require explicit fixture-specific cases before claiming their live coverage. Support diagnostics must use the existing scoped session/reason/audit mechanism, never the bare diagnostics permission alone. Global operations/audit listings can expose unrelated data, so start with role-context `/me` routes; broaden only under approved data-access scope.

No endpoint currently consumes `platform:billing:read`, `platform:billing:refund`, `platform:tenant:suspend`, `platform:technical:write` or `platform:admin:manage`. Do not invent a URL, interpret 404 as successful authorization, or count a login as successful feature coverage. BILLING_ADMIN can pass authentication and denied-access tests, but its permitted platform billing functionality remains unimplemented. Contact APIs lack a customer contact dashboard in this release. These are explicit product limitations, not rollout failures that may be fixed by widening another role.

## Acceptance record and release decision

For each of eleven rows, record independently: bootstrap/provision audit reference, successful HTTP sign-in, wrong-password rejection, GET /me role/scope match, allowed case, denied case, tenant boundary, logout invalidation, interface access and test cleanup. Initial status for every field is **NOT RUN**. BILLING_ADMIN allowed-feature status is **UNAVAILABLE — no implementation**, separate from its not-run authentication fields. Additional permission cases remain pending until their approved fixture evidence exists.

Stop on any unexpected status, data disclosure, role drift, unknown fixture, logged secret or lost commit response. Capture only safe failure codes and operation references. Do not declare all functionality working while unavailable/pending cases remain. A final reviewer may accept documented absent product surfaces as a scope exception, but cannot relabel them tested/passed. Live success may be reported only after actual authorized HTTP/interface evidence is recorded; no local test result fills this record.
